# Browser and Server P2P Deployment

This deployment has two layers:

1. The API/seed/relay processes form the server libp2p mesh.
2. Browsers enroll through `/api/visitors/enroll` and use the advertised relay multiaddr.

## Required peer addresses

Do not commit real peer IDs or private addresses. Copy `.env.p2p.example` to a deployment-only `.env.p2p` file and replace every `<...>` placeholder with the actual peer ID generated by the corresponding identity file.

Required public routes:

- `relay.muhanai.com:4002/tcp` — public TCP/WebSocket relay listener
- `seed.muhanai.com:4001/tcp` — bootstrap/DHT node
- `api.muhanai.com:3001` — API and browser enrollment endpoint

## Start order

```text
1. seed: P2P_DHT_SERVER=true, P2P_RELAY_SERVER=true
2. relay: P2P_RELAY_SERVER=true, bootstrap to seed
3. api: bootstrap to seed, VISITOR_RELAY_MULTIADDR set to relay multiaddr
4. web: built and served by the worker
```

After each node starts, read its actual peer id from its startup log. Never use `12D3KooSEED...` or another placeholder in production.

## Browser flow

The web app:

1. creates or restores an Ed25519 identity in `localStorage`;
2. enrolls with the API;
3. dials the advertised relay multiaddr;
4. subscribes to `/agentmesh/pulse/1.0.0`;
5. publishes a signed-by-identity libp2p presence message;
6. refreshes the visitor session every 30 seconds.

If `VISITOR_RELAY_MULTIADDR` is unset, the browser falls back to HTTP presence enrollment and the dashboard remains functional without pretending that a WebRTC peer exists.

## Firewall

Allow TCP 4001 on seed and TCP 4002 on relay. If TLS terminates at a reverse proxy, proxy WebSocket upgrades and keep the advertised multiaddr aligned with the public hostname.

## Verification

```bash
curl -s https://api.muhanai.com/api/visitors/peers
curl -s https://api.muhanai.com/api/nodes
curl -s https://api.muhanai.com/api/health
```

A browser with WebRTC support should show its `browser-<uuid>` node in `/api/nodes` and emit `muhanai:peer-pulse` events in the page runtime.
